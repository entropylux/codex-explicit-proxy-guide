# Codex：关闭 TUN 后仍可远程控制

[English](README.en.md)

在 Windows 上，曾经只有开启代理软件的 TUN 模式，Codex 才能使用跨设备远程控制。为 Codex 配置显式代理并完整重启后，已实际验证：关闭 TUN，另一台设备仍能远程连入。

这是一份排查经验和复现步骤，适用于本地代理已能正常访问相关服务的环境。

## 问题与判断

浏览器能联网，并不能说明所有 Codex 后台连接都采用了系统代理。系统代理需要应用主动使用；显式代理变量同样取决于网络组件支持；TUN 则能在网络层接管更多连接。

两台电脑的对比提供了线索：无需 TUN 的电脑已有 Codex 专用代理环境配置，而依赖 TUN 的电脑缺少该配置。补齐配置并重启后，后台进程出现到本地代理的连接，代理软件识别为 HTTP CONNECT；随后完成了关闭 TUN 后的跨设备远程连接测试。

这些结果支持优先检查显式代理路径。各组件具体如何加载变量仍可能随版本变化，应以实际连接和远程测试为准。

## 配置方法

1. 保持代理软件运行，开启系统代理，确认 HTTP 或混合端口；下文的 `7890` 仅为示例。
2. 在规则模式中，让 `chatgpt.com`、`openai.com` 及其子域名走可用代理。
3. 在 `%USERPROFILE%\.codex\.env` 中配置：

```dotenv
HTTP_PROXY=http://127.0.0.1:7890
HTTPS_PROXY=http://127.0.0.1:7890
ALL_PROXY=http://127.0.0.1:7890
NO_PROXY=localhost,127.0.0.1,::1
```

也可以先阅读仓库中的 [configure-proxy.ps1](configure-proxy.ps1)，再在 PowerShell 中执行：

```powershell
.\configure-proxy.ps1 -ProxyPort 7890
```

脚本检查端口、备份已有 `.env`、保留其他配置，只更新这四项变量。它不修改系统代理、TUN、DNS、防火墙或 Windows 永久环境变量。已有自定义代理绕过列表时，请先确认是否需要保留额外条目；脚本会将 `NO_PROXY` 更新为上述本地地址列表。

4. 保存工作，完整退出 Codex（包括仍在运行的托盘实例），保持代理软件运行，关闭 TUN，再重新打开 Codex。
5. 分别测试普通对话、另一设备实际连入，以及一段时间内的持续使用。

`.codex/.env` 在本次环境中奏效；如其他版本重启后仍未采用代理，应检查该版本支持的环境加载方式，不要只凭文件存在判断成功。

## 如何判断成功

按证据强度逐步验证：

- **配置存在**：只能说明设置已保存。
- **实际代理连接**：Codex 后台和桌面网络进程连到本地代理端口；代理软件能看到相关目标域名和代理规则。
- **服务入口可达**：HTTPS 证书验证通过并收到响应。普通 GET 返回 `426 Upgrade Required`，说明到达了要求 WebSocket 升级的入口。
- **远程控制可用**：关闭 TUN 后，另一设备实际连入并执行任务。这才是最终验证。

`426` 不等于 WebSocket 握手成功；普通对话可用也不等于远程控制可用。日志中的本机执行端成功连入中继是有用证据，但仍要结合实际跨设备测试。

## 如果仍然失败

- 核对端口和协议：以上 URL 需要 HTTP 或支持 HTTP CONNECT 的混合端口。
- 核对进程是否完整重启，以及后台实际是否连接本地代理。
- 检查域名分流与 `NO_PROXY`，避免相关连接直连。
- 按时间对应远程 WebSocket 错误；区分本机执行端中继和其他远程连接的日志。
- 比较同一网络、同一节点下的表现。短时延迟最低的节点未必有最好的长连接和实际使用体验。

保持 TUN 作为需要时可用的备选方案。远程控制通常不需要为了中继连接开放公网入站端口。

## 回退与隐私

如果原来有 `.env`，从脚本生成的备份恢复；如果原来没有文件，只移除新增的四项变量，并保留后来添加的其他内容。完整重启 Codex 后重新验证。

分享诊断材料时，删除用户名、具体本地路径、网络地址、设备与账号标识、令牌、Cookie、代理密码、订阅地址及原始连接日志。本仓库仅包含通用示例。
